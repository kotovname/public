## Три подхода к дискам под Proxmox

### 1) ZFS (рекоммендуемый вариант)
- Когда уместно: быстрые SSD/NVMe, достаточно ОЗУ, желательно ECC.
- Плюсы: снапшоты, репликация, самовосстановление, контроль целостности, компрессия.
- Минусы: ощутимые требования к памяти и качеству/скорости дисков; желательно отдельный SLOG для ускорения синхронных записей.

### 2) Аппаратный RAID + ext4 (самый простой вариант)
- Когда уместно: есть контроллер с BBU/кэшем, нужна «ставь и поехали».
- Плюсы: минимальная сложность на уровне ОС, ext4 предсказуем и надёжен.
- Минусы: зависимость от конкретного RAID‑контроллера/формата; миграции сложнее, чем с mdadm/ZFS.

### 3) mdadm (RAID) + Debian → апгрейд до Proxmox (мой вариант)
- Когда уместно: хочется прозрачности софта, переносимости массивов и полного контроля.
- Плюсы: независимость от железа, гибкость, понятные процедуры восстановления.
- Минусы: больше ручной работы на этапе установки, особенно с EFI и загрузчиком.

## На практике (в общих чертах)
1. **Разметка дисков (GPT):** на каждом диске отдельный ESP/EFI (вне RAID), остальное — под RAID1 сделано с помощью sgdisk.
2. **Сборка RAID в mdadm:** создаётся массив с помощью mdadm из двух дисков /dev/disk/by-id/* с суперблоком --metadata=1.2 --name=kvm-raid1
3. **Установка Debian на mdadm‑том:** Использовался net-install-debian13.iso при установке вручную указал ESP на каждом диске и следил, чтобы загрузчик ставился на обе ESP, а LVM на kvm-raid1. При желании можно собрать RAID в установочнике.
4. **Базовая сеть:** завёл статический IP для будущего веб‑интерфейса Proxmox; убедился, что имя хоста и DNS‑запись согласованы. Для VM - dhcp
5. **Апдейт системы и ядра:** Обновил Debian 13 sudo apt update && sudo apt upgrade-full, проверил RAID1 с помощью cat /proc/mdstat.
6. **Апгрейд до Proxmox:** подключил репозитории Proxmox, установил необходимые пакеты (pve‑stack, pve-proxy, ядро Proxmox), перезагрузился в pve‑kernel, удалил Debian kernel 6.12.*.
7. **Репозитории:** отключил enterprise‑репо (если нет подписки), включил no‑subscription — для обновлений.
8. **Добавление ВМ:** веб‑интерфейс по https://<host>:8006, добавление /srv/* как storage, создание vmbr1, vmbr2 (мосты) для ВМ, миграция *.qcow2 дисков через скрипт

## Проблемы после установки и как решал

### 1) pveproxy не стартует: ошибка про имя узла
**Симптом:** в логах «Unable to resolve node name … to a non‑loopback IP address»; пред‑скрипты pvecm/updatecerts падают.
**Что помогло (в общем):**
- Привести к единому **hostname** (hostnamectl) и прописать его в **/etc/hosts** на реальный IP (не 127.0.1.1).
- Убедиться, что DNS и обратное разрешение корректны.
- Обновить сертификаты кластера/узла и перезапустить сервисы Proxmox.

### 2) EFI/GRUB при RAID и отдельном ESP
**Симптом:** установщик норовит поставить загрузчик не туда или только на один диск; иногда создаёт ESP «внутри» RAID.
**Что помогло:**
- Держать **ESP отдельно на каждом диске** (не в RAID), чётко указывать их на этапе установки.
- Убедиться, что записи загрузки созданы для обоих дисков; проверить через утилиту управления записями EFI.
- После установки — убедиться, что обе ESP содержат актуальные файлы загрузчика.

### 3) md‑устройства названы md127 и т.п.
**Симптом:** массивы получают «плавающие» имена (md127), что путает.
**Что помогло:**
- Зафиксировать массивы **в конфиге mdadm** (ARRAY … name=…), затем пересобрать initramfs. После этого имена становятся предсказуемыми.

### 4) Сеть после апгрейда до Proxmox
**Симптом:** веб‑интерфейс недоступен, нет моста vmbr0, либо потерялся маршрут по умолчанию.
**Что помогло:**
- Создать **vmbr0**, переложить на него IP узла, а физический NIC сделать портом моста.
- Проверить шлюз и правило для управляемой сети, перезапустить стек сети.

### 5) Репозитории и обновления
**Симптом:** apt ругается на enterprise‑репозиторий без подписки.
**Что помогло:**
- Отключить enterprise‑источник и включить **no‑subscription**. После этого обновления ставятся штатно.

### 6) Время и сертификаты
**Симптом:** веб‑браузер жалуется на сертификат, или pvecm/updatecerts ведёт себя странно.
**Что помогло:**
- Синхронизировать время (NTP), затем пересоздать сертификаты и перезапустить службы.

### 7) Импорт уже имеющихся образов (qcow2/raw)
**Симптом:** есть образы за пределами «хранилищ» Proxmox; команда `qm set … --scsi0 /путь/к.qcow2` не принимает путь «как есть».
**Что помогло (по смыслу):**
- Сначала **добавить правильное хранилище** (Directory/LVM‑thin/ZFS) в конфигурации Proxmox.
- Затем **импортировать** образ в это хранилище (или «переместить/преобразовать»), и только после этого прикреплять диск к ВМ.

## Мини‑чеклист перед эксплуатацией
- Резервные копии: настроить **Proxmox Backup Server** или внешние bkup‑политики; проверить восстановление.
- Мониторинг: smartd, уведомления о деградации RAID, базовые алерты Proxmox, e‑mail отправка.
- Хранилища: решить, где будут образы ВМ (LVM‑thin/Directory/ZFS), задать квоты/тонкое выделение.
- Сеть: убедиться, что vmbr0/маршруты/фильтры соответствуют плану сегментации.
- Обновления: включён **no‑subscription** репозиторий, ручная регулярная проверка обновлений.

## Что бы я сделал иначе в следующий раз
- Сразу планировал бы **отдельный LVM‑thin** под образы ВМ, чтобы комфортно пользоваться снапшотами/клонованием.
- Отдельно проверил бы **резервный путь загрузки** с каждого диска: обе ESP содержат актуальные файлы, обе EFI‑записи активны.
- Сразу добавил бы **Directory‑storage** для временного импорта qcow2, чтобы меньше возиться с путями.
